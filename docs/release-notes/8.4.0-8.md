# Percona XtraBackup 8.4.0-8 (2026-11-25)

Get started with [Quickstart Guide for Percona XtraBackup].

## Release highlights

Percona XtraBackup 8.4.0-8 release includes new features, improvements, and bug fixes.

* Percona XtraBackup introduces the ability to store backup history records on a different, writable server using the new `--history-*` options. This allows taking backups from read-only replicas or Group Replication secondaries without encountering write errors.

* Percona XtraBackup adds clearer option aliases: `--apply-redo-only` (as an alias for `--apply-log-only`), `--backup-incremental-base` (for `--incremental-basedir`), and `--prepare-incremental-from-dir` (for `--incremental-dir`).

We recommend that you download the Percona XtraBackup for the same platform as the MySQL-compatible server. For example, if your server is on an ARM64 platform, you should download and use the Percona XtraBackup for ARM64 for that operating system.

## New features

* [PXB-2559](https://perconadev.atlassian.net/browse/PXB-2559): Adds the `--history-host`, `--history-port`, `--history-socket`, `--history-user`, `--history-password`, and `--history-ssl-*` options to [store backup history on a different server](../store-backup-history.md). Before, Percona XtraBackup always wrote the history record to the server you back up. The write failed when that server ran with `super_read_only` enabled, for example, a replica or a secondary member of a single-primary Group Replication cluster. The `--incremental-history-name` and `--incremental-history-uuid` options also read the base LSN from the history server. (Thanks to Francisco Miguel Biete Banon for contributing the fix for this issue.)

## Improvements

* [PXB-3758](https://perconadev.atlassian.net/browse/PXB-3758): Adds the `--apply-redo-only` option as the new name for `--apply-log-only`. Both names work the same way. If you pass both options in the same command, Percona XtraBackup reports an error and does not start. For details, see [Prepare an incremental backup](../prepare-incremental-backup.md).

* [PXB-3840](https://perconadev.atlassian.net/browse/PXB-3840): Adds phase-specific names for incremental backup options. Use `--backup-incremental-base` instead of `--incremental-basedir` with `--backup`. Use `--prepare-incremental-from-dir` instead of `--incremental-dir` with `--prepare`. The old and new names work the same way. If you pass an old name and its new name in the same command, Percona XtraBackup reports an error and does not start.


## Bug fixes

* [PXB-3800](https://perconadev.atlassian.net/browse/PXB-3800): `xtrabackup` no longer terminates unexpectedly with an assertion failure in `fil_tablespace_redo_extend()` when the redo log contains an `MLOG_FILE_EXTEND` record for the system tablespace. (Thanks to Matthew Kent for contributing the fix for this issue.)

* [PXB-3882](https://perconadev.atlassian.net/browse/PXB-3882): The debug build now compiles with gcc 15.

* [PXB-3885](https://perconadev.atlassian.net/browse/PXB-3885): `xbcloud` now runs the retry waits of parallel requests at the same time. Previously, when the network was slow or unavailable, several failed requests took the sum of their backoff delays instead of the longest delay.

* [PXB-3889](https://perconadev.atlassian.net/browse/PXB-3889): `xtrabackup --prepare --use-free-memory-pct` no longer terminates unexpectedly with a segmentation fault on operating systems that use `libproc2` (such as RHEL 10, Debian 12 and 13, and Ubuntu 24.04). (Thank you to Alexander Olekhnovich for your contribution)

* [PXB-3894](https://perconadev.atlassian.net/browse/PXB-3894): `xbcloud get` now works on Azure Blob Storage containers with Hierarchical Namespace (HNS) enabled. Previously, directory entries were parsed as backup chunks, which caused the restore to fail.
